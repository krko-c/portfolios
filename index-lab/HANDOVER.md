# Index Lab — 인수인계 문서

> 새 대화를 시작할 때 이 문서를 먼저 읽어주세요.

## 1. 이 프로젝트가 무엇인가

**규칙 기반 ETF·인덱스 설계·검증 도구**입니다. Portfolio Analyzer가 "이미
정해진 포트폴리오가 괜찮은가"를 분석한다면, Index Lab은 "투자 아이디어를
어떤 규칙으로 종목·비중으로 바꿀 것인가"를 다룹니다.

- 위치: `portfolios` 저장소 안 `index-lab/` 폴더 (완전히 독립된 코드베이스,
  `app.py`를 import하지 않음 — 재사용은 함수 복사 방식)
- 구조: `core/`(계산, Streamlit 의존 없음) + `pages/`(화면) + `tests/`(pytest)
- 목적: **실제 ETF/인덱스 상품화 검토용**으로 시작 (개인 리서치용보다 무겁게)
- 현재 단계: 1단계(규칙 기반 MVP) 완료. 최적화 solver·블랙-리터만·
  Point-in-Time 데이터·감사로그는 없음 (2단계 이후)
- 데이터: yfinance(가격)만 확정. DART(종목정보) 연동 중 — 실 API 키로
  검증 안 됨(개발 환경 네트워크 차단). ECOS/FRED는 거시지표라 종목 단위
  데이터가 필요한 이 도구엔 우선순위 낮음
- 저장: 세션 상태 + JSON 다운로드/업로드만. 서버 파일 저장 없음 (여러 명이
  같은 배포 인스턴스를 쓰면 세션 간 데이터가 섞이는 문제를 Portfolio
  Analyzer에서 겪고 처음부터 피함). **실제로 여러 명이 협업 시작하면 그때
  진짜 저장소(SQLite 등)로 바꾸기로 합의됨.**

## 2. 작업 방식 (반드시 지켜주세요)

### 2-1. 계산 로직은 반드시 먼저 테스트

`core/`에 새 함수를 넣을 때는 **합성 데이터로 정답을 미리 계산해두고
단위테스트부터 통과시킨 뒤** 화면에 연결하세요. 실제로 이 순서를 지켜서
개발 중 설계 결함 하나를 테스트가 잡았습니다(아래 5절 참고).

```bash
cd index-lab
python -m pytest tests/ -v
```

### 2-2. 화면 붙인 뒤 반드시 실제로 클릭해서 확인

Streamlit 멀티페이지 앱은 **사이드바 링크를 클릭해야** `session_state`가
유지됩니다. Playwright로 테스트할 때 `page.goto(url)`로 직접 이동하면
세션이 끊겨서 "1단계를 먼저 완료해주세요" 경고만 뜨는데 이게 오류 없이
렌더링되니 **거짓 성공(false positive)**으로 오판하기 쉽습니다. 실제로
이 세션에서 한 번 이렇게 잘못 판단했다가 재검증에서 잡았습니다.

```python
# 틀림 — 세션이 끊김
page.goto(f"{BASE}/적격성_필터")

# 맞음 — 실제 사용자 동선
page.locator("[data-testid='stSidebarNav'] a", has_text="적격성 필터").click()
```

각 단계 결과가 **실제로 화면에 나타나는지**(빈 경고 문구가 아니라)까지
텍스트로 확인하세요. "에러 안 남" 만으로는 부족합니다.

### 2-3. 이 개발 환경의 제약

- yfinance·DART·ECOS 등 외부 네트워크 전부 차단. 실제 데이터 조회 화면은
  입력 UI 로드까지만 확인 가능
- 샘플 데이터(`1_데이터_유니버스` 화면의 "샘플 데이터로 먼저 해보기"
  체크박스)로 1~5단계 전체 파이프라인은 끝까지 검증 가능
- DART 연동은 공식 API 스키마 기준으로 짜고 모킹(가짜 응답)으로 파싱
  로직만 검증했습니다. **실제 키로 첫 호출은 배포 후 사용자가 확인해야
  합니다.**

### 2-4. 응답 스타일

Portfolio Analyzer와 동일 — 한국어, 결론부터, 표·짧은 문단 위주, 실수는
감추지 말고 인정, 코드블록은 필요할 때만.

## 3. 이 도구를 관통하는 원칙

### 3-1. 규칙은 결정론적이어야 한다

같은 입력에는 항상 같은 결과가 나와야 합니다. 최적화 solver·AI 자동판단을
쓰지 않는 이유입니다. `weighting.py`의 상한 재배분(iterative capping)도
반복 알고리즘이지만 수렴 조건이 명확해 결정론적입니다.

### 3-2. 조용히 제외하지 않는다

`validation.py`·`filters.py`는 문제가 있거나 필터에서 빠진 종목을 전부
**이유와 함께** 로그로 남깁니다. Portfolio Analyzer의 "화면과 계산의
일치" 원칙과 같은 맥락입니다.

### 3-3. 버퍼룰은 보유 종목을 우선 보호한다

목표 인원을 초과할 때 순위로만 자르면 버퍼룰의 존재 이유(불필요한 회전율
방지)가 무너집니다. `selection.py`는 "유지" 후보를 먼저 확정하고, 남는
자리만 "신규편입" 후보로 채웁니다. 인원이 넘치면 신규편입 쪽부터
자릅니다.

### 3-4. 탐색형 백테스트임을 숨기지 않는다

Point-in-Time 데이터가 없는 한, `6_정기변경_백테스트` 화면은 **현재
선정된 종목·비중을 과거 가격에 그대로 적용**합니다(생존편향 있음). 화면
상단에 항상 경고를 표시합니다. 이 결과를 방법론 최종 검증 근거로 쓰면
안 됩니다.

## 4. 현재 화면 구성

```
app.py                          진입 화면 — 프로젝트 개요, 1단계 범위 안내
1_📥_데이터_유니버스.py          업로드 + 품질점검 (샘플 데이터 지원)
2_🔍_적격성_필터.py              필터 깔때기 + 종목별 사유 로그
3_📊_점수_설계.py                요인 선택 + 가중치·방향·방식
4_✅_구성종목_선정.py             목표종목수 + 버퍼룰 + 직전구성 입력
5_⚖️_비중_설계.py                비중 5방식 + 종목/산업 상한
6_📅_정기변경_백테스트.py        yfinance 실가격, 탐색형 경고 표시
7_🔀_방법론_비교_및_출력.py      비중방식 대안비교 + JSON/Excel 출력
```

### core/ 함수 위치

| 파일 | 핵심 함수 |
|---|---|
| `validation.py` | `check_universe` — 데이터 품질 점검 |
| `filters.py` | `apply_eligibility` — 적격성 필터 + 깔때기 |
| `scoring.py` | `compute_score` — 종합점수 (zscore/percentile/raw) |
| `selection.py` | `select_constituents` — 선정 + 버퍼룰, `current_constituents` |
| `weighting.py` | `compute_weights`, `apply_caps`(+ `_iterative_cap`) |
| `index_simulator.py` | `simulate_index` — 정기변경 반영 동적 백테스트 |
| `analytics.py` | `cagr`, `sharpe_ratio`, `sortino_ratio`(수정된 공식), `relative_wealth` 등 |
| `export.py` | `methodology_to_json`, `build_excel` |

## 5. 반복해서 지적받은 것들 (같은 실수 금지)

### 5-1. 소르티노 하방편차 공식

`e[e<0].std()`(부분집합 표준편차)는 **틀린 공식**입니다. Portfolio
Analyzer에서 최대 41% 과대평가·표본크기 둔감 문제를 발견·수정했고,
`index-lab/core/analytics.py`는 처음부터 올바른 공식(`sqrt(mean(min(e,0)²))`,
전체 표본 기준)을 씁니다. `tests/test_analytics.py`에 재발 방지 테스트가
있습니다 — 지우지 마세요.

### 5-2. 회전율은 직전 종료 비중을 넘겨야 한다

매 정기변경을 100% 재구축으로 계산하면 비용이 부풀려집니다.
`index_simulator.py`는 `_segment_returns`가 돌려주는 `end_w`(구간 종료
시점의 드리프트된 실제 비중)를 다음 구간의 `prev_end_w`로 넘겨, 실제
교체분만 회전율로 잡습니다. `test_index_simulator.py`의
`test_rebalance_turnover_reflects_actual_drift_not_full_rebuild`가 이걸
검증합니다.

### 5-3. 상한 초과분을 한 번만 재배분하면 안 된다

A를 상한으로 자른 뒤 B에 몰아주면 B가 다시 상한을 넘을 수 있습니다.
`_iterative_cap`은 초과 여부를 반복 재확인합니다.
`test_iterative_cap_cascading_overflow`가 이 케이스를 검증합니다.

### 5-4. 초과분 재배분 시 버퍼로 보호된 종목부터 자르면 안 됨

3-3 참고. `test_buffer_keeps_previously_held_name_that_slipped_slightly`가
이 회귀를 잡아냅니다 — 처음 구현했을 때 실제로 이 버그가 있었습니다.

## 6. 아직 안 한 것

### 6-1. 진행 중

- **DART 연동** (`core/dart_client.py` 예정) — 종목 상장일·업종·기업개요를
  API로 자동 조회. 실제 키로 미검증.

### 6-2. 2단계(2단계 실무 방법론 강화, 순서 없음)

- 핵심군·확장군(core/extended) 분리
- 국가별 상한 (산업 상한과 같은 매커니즘 재사용 가능)
- IPO·상장폐지·합병 등 기업행동 반영
- Point-in-Time 데이터 검증 — **유료 벤더 없이는 근본적으로 제한적**.
  DART가 과거 시점 재무제표는 주지만, 과거 시점의 "전체 유니버스가
  무엇이었는가"(그 시점에 상장돼 있던 종목 전체 목록)는 별도 문제
- 감사로그, 방법론 버전관리
- 룰북 Word 출력 (docx 스킬로 가능)

### 6-3. 3단계 이후

- 테마 관련성 AI 분석 (사업보고서·IR 자료 기반, 사용자 승인 필수 —
  자동 편입 금지 원칙 유지)
- 데이터 자동화, 정기 스냅샷 적재
